## Лабораторна робота 2: Inverted Index

### 1. Бенчмарк булевого пошуку (Merge vs Set)
Запит: `"the AND and"`
* **Two-pointer merge:** ~0.00025 сек
* **Python set intersection:** ~0.00013 сек

**Висновок:** Пошук через перетин множин (`set`) відпрацював удвічі швидше. Це пов'язано з тим, що операція `&` для множин оптимізована і виконується на рівні мови C, тоді як наш алгоритм `merge` працює через цикл `while` у самому інтерпретаторі Python. Проте алгоритм злиття (`merge`) є більш універсальним: він не вимагає завантаження всіх `doc_id` у хеш-таблиці та дозволяє працювати з постінгами потоково.

### 2. Дослідження споживання пам'яті індексом
Заміри `tracemalloc` на корпусі (802 документи, 346 786 термінів):

| Варіант зберігання                    | Пік пам'яті | Розмір файлу (pickle) | Час збереження |
|---------------------------------------|-------------|-----------------------|----------------|
| `list[Posting]` (звичайний dataclass) | ~187.41 MB  | 15.45 MB              | 2.23 s         |
| `list[Posting]` (`slots=True`)        | 187.37 MB   | 15.44 MB              | 2.25 s         |
| `array('I')` (пари `doc_id`, `tf`)    | 156.49 MB   | 14.78 MB              | 0.73 s         |

**Куди йдуть байти?**
Звичайний клас або `@dataclass` у Python резервує прихований словник `__dict__` для кожного екземпляра, що додає накладні витрати по пам'яті. Використання `slots=True` прибирає цей словник, жорстко фіксуючи структуру атрибутів (хоча на нашому обсязі даних різниця виявилася в межах похибки `tracemalloc`). Найбільшу реальну економію (~30 MB) дало використання `array('I')`. У цьому випадку ми повністю відмовляємося від створення об'єктів Python на кожен постінг. Замість мільйонів об'єктів із вказівниками та метаданими, ми зберігаємо "сирі" 4-байтні беззнакові цілі числа (unsigned ints) суцільним блоком у пам'яті, що кардинально зменшує overhead та пришвидшує серіалізацію.
